个人信息处理规则偏离实践只有一个方向：实践往前走，处理规则停在原地。某份 PIA 批准了新的数据类别；某份 DPA 签了一个处理规则里没列出的下游处理者；某项分诊有条件批准了新用途，附带一个处理规则还没写进去的披露要求。几个月后，处理规则已经不再反映实际情况。本指引用于在漂移成为问题之前发现它。

## 适用情形

- **定期扫描**：每周（或按团队频率）检查自上次扫描以来新产出的 PIA、DPA 审查、分诊结论和权利请求回复，找出处理规则需要更新的地方。建议在日历或任务管理工具中设置每周提醒。
- **直接查询**：业务提出「我们想开始做 X」，判断处理规则是否已覆盖、需要怎样修改。

本指引不包括：直接修改处理规则（只起草建议语言，每项修改由人审核批准）；跟踪外部法规变化（属于法规差距分析）；从邮件或即时通讯中的非正式决定里找漂移（只扫描已归档的结构化成果）。

## 需要准备的材料

- 公司适用的监管制度范围（《个人信息保护法》《数据安全法》《网络安全法》、行业监管等）。
- 已发布的个人信息处理规则全文——它是起草修改时的权威来源，摘要不能替代。
- 处理规则承诺摘要：数据类别、处理目的、保存期限、第三方、提供的用户权利。
- 归档成果的位置（PIA、DPA 审查、分诊结论、权利请求回复）和上次扫描日期。
- 其他承诺表面的位置和最近更新日期（见下文）。

## 先确认扫描范围：所有承诺表面

网站处理规则只是一个表面。至少还有四处作出了有约束力的承诺，同样会被监管部门检查一致性：

1. **Cookie 同意横幅 / 同意管理平台（CMP）。** CMP 承诺了具体的 Cookie 类别和目的。处理规则写「我们使用分析 Cookie」而 CMP 只提供「仅必要」的，即存在冲突。网信办和市场监管部门已对 CMP 配置错误采取执法行动。
2. **应用商店隐私标签。** Apple App 隐私标签和 Google 数据安全标签是自行声明、可被追责的。处理规则更新了而标签没更新，就是监管部门看得见的实质不一致。检查：标签上次何时更新？与处理规则声明的数据类别、目的和共享是否一致？
3. **产品内同意流程。** 用户实际作出选择的界面（引导同意、设置开关、「我们已更新处理规则」弹窗）。处理规则说公司会做什么，同意流程说用户同意了什么，二者应一致。
4. **行业特定通知。** 金融、医疗健康、未成年人等领域有各自的通知义务，网站处理规则不能替代。

为每个表面登记位置和最近更新日期。扫描时逐个比对，并标出偏离，例如：「处理规则更新于【日期】，应用商店标签上次更新于【更早日期】，可能未反映新数据类别；CMP 上次配置于【日期】，须核实 Cookie 目的与处理规则一致。」处理规则干净而应用商店标签过时，就是一桩等着发生的投诉。

### 行业通知的比对

适用制度包含以下内容的，除网站处理规则外，还要与行业通知比对；没有配置行业通知的，标明缺失：

| 适用制度 | 需比对的行业通知 | 需要标出的内容 |
|---|---|---|
| **金融**（个人金融信息保护技术规范、征信业管理条例） | 金融领域个人信息处理特别告知 | 成果中出现的新金融信息类别、与非关联第三方的共享或选择退出机制变化，而行业通知未反映 |
| **医疗健康**（人口健康信息管理办法、个保法） | 健康医疗数据处理的特别告知 | 新的使用或披露、新的常规类别、患者权利机制的变化 |
| **未成年人**（儿童个人信息网络保护规定、个保法第31条） | 面向监护人的直接通知和在线通知 | 从未成年人收集的新数据类别、新的第三方披露、监护人同意机制的变化 |
| **汽车数据**（汽车数据安全管理若干规定） | 汽车数据处理的特别告知 | 受规定限制的处理活动，而通知未反映 |

- 适用制度中某项没有配置行业通知的，**每次扫描都列为存续缺口**，直到解决，而不是只提一次。扫描报告中写明：
  > **行业通知覆盖：**
  > - 【制度】：【已配置的通知位置 + 最近更新日期，或「未配置——每次扫描标出直至解决」】
- 找不到行业通知的，明确写出来，不要默默只比对网站处理规则。
- 登记的适用制度与实际不符的（例如只列了个保法和数安法，但扫描到的成果涉及健康医疗、金融或未成年人数据），先指出错配，确认是否应把该制度加入适用范围、是否有对应的行业通知需要比对。

## 办理步骤：定期扫描

### 1. 确定范围

扫描上次扫描日期之后归档的成果。没有记录日期的，扫描全部并注明「首次扫描，扫描全部成果」。没有新成果的，记录「自【上次扫描日期】以来无新成果，处理规则与近期实践看起来一致，下次扫描：【日期】」。扫描完成后把上次扫描日期更新为当天。

### 2. 按成果类型提取信息

| 成果类型 | 提取 | 标出 |
|---|---|---|
| PIA | 数据类别、目的、第三方 / 受托处理者、保留期限、用户权利影响、提出的处理条件 | 不在当前处理规则承诺中的任何内容 |
| DPA 审查（已签署或已批准） | 新增下游处理者、约定的数据位置、覆盖的处理目的、DPA 对个人信息主体设定的义务 | 处理规则未列出的下游处理者（处理规则有列举的）、新处理类别、新数据位置、与处理规则不一致的义务 |
| 分诊结论（需做影响评估 / 可直接推进） | 批准了什么；附带的隐含公开承诺的条件（如「上线前须向受影响方披露」） | 已批准但处理规则未覆盖的做法；需要写入处理规则的条件 |
| 权利请求回复 | 以往请求中未出现过的数据类别；新加入系统清单的系统 | 已收集但处理规则未声明的数据类别 |

### 3. 判断差距级别

- **必须更新**：处理规则作出的承诺与成果相抵触，或处理活动正在进行而处理规则完全没有覆盖。不更新即构成实质性不实陈述。
  > 例：处理规则写「我们收集姓名、邮箱和支付信息」，某份 PIA 批准了收集位置数据，处理规则对位置只字未提。这是必须更新——公司在收集未披露的数据。
- **建议更新**：处理规则未提及，但不冲突。不更新也说得过去，更新后更完善。
  > 例：处理规则写「我们可能与服务提供方共享数据」，某份 DPA 签了新的数据分析供应商。处理规则没写该供应商名称，但也不排除。建议加入维护中的下游处理者名单。

### 4. 起草建议语言并出具报告

见下文「文书结构：扫描报告」。

## 办理步骤：直接查询

### 1. 解析拟议做法

- 收集或处理什么数据？
- 目的是什么？
- 还有谁参与（供应商、合作伙伴、第三方）？
- 个人信息主体是谁？
- 有没有自动化决策？
- 是否需要向个人作出新的披露？

描述模糊的，只问一个澄清问题，不做冗长录入——这个模式要快。

### 2. 与处理规则比对

| 检查点 | 当前处理规则 | 拟议做法 | 判定 |
|---|---|---|---|
| 数据类别 | 【处理规则所列】 | 【新类别，如有】 | 🟢 已覆盖 / 🟡 差距 / 🔴 冲突 |
| 目的 | 【已声明目的】 | 【新目的】 | |
| 第三方 / 下游处理者 | 【已声明对象】 | 【新对象，如有】 | |
| 保留期限 | 【保留承诺】 | 【隐含的保留期限】 | |
| 用户权利 | 【提供的权利】 | 【对权利的新影响】 | |
| 披露 / 通知 | 【处理规则关于告知用户的表述】 | 【本做法所要求的】 | |

### 3. 出具结论

见下文「文书结构：直接查询」。有必须更新的，处理规则修改应在上线前完成；只有建议更新的，可以先推进，在下次处理规则更新时调整。

## 建议语言的质量标准

- 与现有处理规则的语气和风格一致——起草前先读处理规则全文，而不是只看摘要。
- 足够具体才有意义，但不能具体到日常变动就会失效（「为协助我们运营业务的服务提供方」比逐一列出供应商名称更耐用）。
- 不作公司兑现不了的承诺（架构中位置数据会流向分析供应商的，不能写「我们绝不共享位置数据」）。
- 指出哪些地方需要处理规则整体立场的调整，而不只是加一句话。
- 写明加到哪一章节；合适的章节不存在的，说明并建议新设。

## 常见风险

- 只比对网站处理规则，漏掉 CMP、应用商店标签、产品内同意流程和行业通知。
- 行业通知缺失只提一次，后续扫描不再跟踪。
- 适用制度登记不全，导致行业通知没有被纳入比对。
- 建议语言作出团队无法兑现的承诺。
- 团队没有把 PIA 等成果归档，扫描找不到。

## 文书结构

### 扫描报告

```markdown
【工作成果标头】

# 个人信息处理规则监控——扫描报告

**日期：** 【日期】
**已扫描成果：** 【N 个文件】 | **自上次扫描以来新增：** 【N 个文件】
**发现的差距：** 【N】项必须 | 【N】项建议

---

## 必须更新

### 【差距1 简称】

**来源：** 【触发该差距的文件名 / 成果类型】
**实际情况：** 【新做法的通俗描述】
**当前处理规则：** 【引用相关章节，或「未覆盖」】
**差距：** 【缺什么或哪里不一致】

**建议语言：**
> *添加至【章节名称】：*
> 「【起草的处理规则文本——具体，与现有处理规则风格一致】」

---

【每个必须更新的差距重复上述格式】

---

## 建议更新

### 【差距名称】

**来源：** 【文件名】
**实际情况：** 【描述】
**当前处理规则：** 【引用或「未提及」】
**建议语言：**
> *添加至 / 更新【章节】：*
> 「【起草文本】」

---

## 行业通知覆盖

- 【制度】：【通知位置 + 最近更新日期，或「未配置——每次扫描标出直至解决」】

---

## 无需行动

【列出已扫描且未发现差距的成果，确认已审阅】

---

## 后续步骤

- [ ] 审阅必须更新事项——每项都需在相关功能 / 处理活动上线前（已上线的立即）作出决定
- [ ] 审阅建议更新事项——紧迫性较低，在下次处理规则更新时处理
- [ ] 下次扫描：【日期】
```

### 直接查询

```markdown
【工作成果标头】

# 个人信息处理规则检查：【一句话概括拟议做法】

**结论：** 【需更新处理规则 / 建议更新 / 无需更新】

---

## 已覆盖

【拟议做法中已被现行处理规则覆盖的方面，简要列出，确认无需改动】

## 缺失

### 【差距1】

**当前处理规则：** 【引用或「未提及」】
**为什么需要：** 【法律、声誉或一致性方面的原因】

**建议语言：**
> *添加至【章节】：*
> 「【起草文本】」

### 【差距2】
【同上格式】

## 冲突

### 【冲突1，如有】

**当前处理规则：** 【引用】
**拟议做法：** 【冲突之处】
**解决：** 【哪一方需要改、为什么——通常是调整做法以符合处理规则，或把处理规则更新到可辩护的新立场】

---

## 时机

【有必须更新的：「处理规则修改应在上线前完成。」
只有建议更新的：「可以推进，在下次处理规则更新时调整。」】
```

工作成果标头：律师出具的写「保密——律师工作成果——按照律师指示准备」；非律师出具的写「研究笔记——非法律意见——在行动前应由执业律师审阅」。

完成后给出下一步选项：起草处理规则修改稿；升级报批；补充事实；暂缓观察（记入台账并写明复查时间）；其他。发现超过约 10 项的，可整理成按表面（处理规则条款 / PIA / DPA / 分诊）和严重程度计数、附来源和整改建议的可排序清单。

## 法律依据

- 《个人信息保护法》第31条（不满十四周岁未成年人个人信息）
- 《个人金融信息保护技术规范》、《征信业管理条例》
- 人口健康信息管理办法
- 《儿童个人信息网络保护规定》
- 《汽车数据安全管理若干规定》
