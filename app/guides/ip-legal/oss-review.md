本篇用于对依赖清单、单个库或准备对外开源的自有代码做开源许可证合规检查：按许可证族分类，把义务对应到部署模式，标出许可证不明和“伪开源”的包，并给出处理建议——履行义务、替换、移除、交律师审查或购买商业许可。

这是初步分类。著佐权（copyleft）义务是否触发，取决于部署模式、链接方式、管辖，有时还取决于尚未经法院检验的问题（如 AGPL 的“通过网络交互”）。凡被归为强著佐权或许可证不明的，在依赖上线或代码发布前须经律师评估。

## 适用情形

- 审查 `package.json`、`requirements.txt`、`go.mod`、`Gemfile`、`Cargo.toml`、`pom.xml`、锁定文件或 SBOM（SPDX / CycloneDX）；
- 评估是否可以引入某个库；
- 准备把自有代码开源，检查其中嵌入了什么；
- 开源合规请求常通过工单系统提出，可逐单处理。

## 需要准备的材料

- 依赖清单、库名或仓库；
- 部署模式（见第2步）；
- 团队的开源政策（如有）：哪些许可证可直接使用、哪些需审查、哪些禁止，以此为准；
- 团队的开源审查分工（通常工程师 + 法务签署）和著佐权问题的上报路径。

## 办理步骤

### 1. 确定审查范围

| 范围 | 分析路径 |
|---|---|
| 依赖清单 | 逐项分类，汇总义务 |
| 单个库 | 分类该包；能取得的，同时梳理其传递依赖 |
| 对外发布的自有代码 | 检查嵌入了什么（直接和传递依赖），所选发布许可证是否与所有嵌入许可证兼容，LICENSE / NOTICE 文件是否正确 |

### 2. 确定部署模式

这是许可证清单之外最重要的信息：同一个库，交付方式不同，义务不同。

| 部署方式 | 实质相关的许可证 |
|---|---|
| SaaS / 托管服务（用户经网络访问，不交付任何东西） | AGPL（网络触发）；界面中的宽松型署名义务；转售为竞争性服务时的 SSPL / BUSL / Elastic |
| 分发二进制（桌面应用、移动应用、本地部署服务器、命令行工具） | GPL、LGPL、MPL、EPL（分发即触发）；宽松型署名义务 |
| 仅内部使用 | 大多数著佐权不触发（没有分发）；宽松型署名仍是好习惯；公司外部用户经网络交互的，AGPL 仍触发 |
| 嵌入式 / 固件 | GPL 在这里特别难合规（源码披露 + 可复现构建 + 某些情况下的安装信息），应在发布前而不是发布后规划 |

备忘录中写明部署模式。

### 3. 逐包分类

阅读实际许可证文本，不只看元数据：LICENSE 文件可能写错（文件写 MIT 而源码头声明 GPL；README 说 Apache 却没有 LICENSE 文件），包管理器元数据可能过时。

| 类别 | 示例 | 关键义务 |
|---|---|---|
| 宽松型 | MIT、BSD-2-Clause、BSD-3-Clause、Apache-2.0、ISC、Zlib、Unlicense | 署名、保留许可证文本；Apache-2.0 另有专利授权和 NOTICE 要求 |
| 弱著佐权 | LGPL-2.1、LGPL-3.0、MPL-2.0、EPL-1.0、EPL-2.0、CDDL | 文件级或库级源码披露，链接规则各不相同 |
| 强著佐权 | GPL-2.0、GPL-3.0、AGPL-3.0、OSL、EUPL（视版本） | 广泛的源码披露；AGPL 延伸到网络使用 |
| 公有领域 / 权利放弃 | CC0、Unlicense、WTFPL | 通常无义务，但在不承认放弃进入公有领域的法域有争议（如中国法下署名权不可放弃） |
| 非 OSI 认可的源码可见许可 | SSPL、BUSL、Commons Clause、Elastic License、Confluent Community、fair-source 类 | 不是开源，限制商业使用、竞争性服务使用或两者兼有，须读具体许可证 |
| 其他 / 自定义 / 不明 | 厂商自定、专有、缺少许可证文件、许可证文本与源码头冲突 | 停下来审查，不得默认按宽松型处理 |

另外标出：

- **双重许可的包**：本方用的是哪一个？选择不同，义务不同；
- **已停止维护的包**：有没有受支持的替代品；
- **传递依赖中有著佐权的包**：顶层是宽松型，下层依赖是著佐权；
- **近期变更许可证的包**：如 Redis、MongoDB、Elastic、HashiCorp，确认锁定的版本适用的是哪个许可证。

### 4. 判断链接方式，确定义务和风险

链接方式决定著佐权是否真正触发：

| 使用方式 | 判断 |
|---|---|
| 静态链接 / 一起编译 | 合为一个二进制，著佐权触发的强烈信号（LGPL 的“基于库的作品”、GPL 的衍生作品） |
| 动态链接 / 共享库 | 运行时可分离。LGPL 明确允许（“使用库的作品”）；GPL 下有争议 |
| 头文件包含 / 内联函数 | 视包含量多少，可能构成衍生作品 |
| 子进程 / 进程间通信 | 通过明确接口通信的独立进程，一般不构成衍生 |
| 网络接口调用 | 对多数许可证不触发；对 **AGPL**，经网络提供软件即触发，在微服务架构中位于接口之后的 AGPL 组件仍触发 |
| 文件级著佐权（MPL） | 只有被修改的文件受著佐权约束，检查是否修改了这类文件 |

同一许可证，链接方式不同，评级相反：专有产品中静态链接 LGPL 是 🔴 严重，动态链接 LGPL 是 🟢 低。只写“LGPL——弱著佐权，链接规则各异”而不做链接分析，等于没有回答。

**严重程度：**

| 等级 | 含义 |
|---|---|
| 🔴 严重 | 强著佐权处于会触发它的部署中（分发二进制中的 GPL、SaaS 中的 AGPL）；非 OSI 许可证与商业模式直接冲突（本方做托管服务而代码采用 SSPL）；关键依赖的许可证无法确定 |
| 🟠 高 | 团队尚未落实的弱著佐权义务（文件级披露、NOTICE 要求）；双重许可中所选许可证不明；LICENSE 文件与源码头不一致 |
| 🟡 中 | 宽松型但署名要求未纳入构建流程（缺少 NOTICES 文件、分发包中缺少 LICENSE）；传递著佐权是否触发取决于库的使用方式 |
| 🟢 低 | 宽松型且义务已满足；著佐权处于不会触发的部署模式（仅内部使用、不再分发的 GPL 库） |

### 5. 标出重点问题

在备忘录顶部列出：

- **许可证不明**：归为“需审查”，不是宽松型。未分类的依赖应阻止发布决定；
- **LICENSE 文件与源码头冲突**：两者都读，报告冲突；
- **不兼容组合**：GPL-2.0 only 与 Apache-2.0 是历史上已知的不兼容；MPL / EPL / GPL 组合要仔细查；
- **伪装成开源的非 OSI 许可证**：SSPL、BUSL、Commons Clause、Elastic License、Confluent Community，以许可证本身为准，不看代码托管平台的“开源”标签；
- **许可证变更**：早期版本宽松、当前版本为源码可见许可的，锁定版本至关重要。

### 6. 对外开源前的检查

- 所选发布许可证与每个嵌入依赖兼容（例如嵌入了 GPL 代码就不能以 MIT 发布，组合作品须为 GPL）；
- LICENSE 文件存在且正确；
- NOTICE 文件存在并列明所需署名（Apache-2.0 等）；
- 第三方许可证文本已按要求打包；
- 仓库历史中没有专有或保密代码、客户数据、嵌入的凭证；
- 项目名称的商标和品牌政策（与著作权许可分开处理）。

### 7. 形成备忘录

- 备忘录及所审依赖清单可能受保密义务或律师工作成果保护，继承其保密状态；只在保密范围内分发，对外交付前去掉内部工作成果标识。
- 引用许可证文本、解释许可证的判决或管理机构指引时注明出处（OSI、SPDX、FSF、法律数据库、仓库中直接读取的许可证文本等）；凭记忆写出、未经核实的，句末标〔待核〕。
- 检索结果不足以支撑某项规则的，如实报告，不用网络搜索或记忆悄悄补齐；是否扩大检索或采用较低可信度来源，由律师决定。
- 无法有把握分类的，一律标“需审查”，不称为宽松型：基于“默认宽松”作出的发布决定，几个月后可能变成源码披露义务或禁令；多标注的，律师审查时再缩小范围。
- 著佐权是否触发取决于有争议的问题时，交律师审查，并列出双方各自的有利因素。
- 包超过约10个的，可以做成看板：按许可证族（宽松型 / 弱著佐权 / 强著佐权 / AGPL / 专有 / 不明）和风险等级计数，附可按严重程度和版本排序的明细表。
- 收尾时由律师决定下一步：起草文件、上报、补充事实、等待观察或其他。

## 检查清单

- □ 已参照团队开源政策
- □ 分类义务前已确定部署模式
- □ 每个依赖（含传递依赖）都已分类
- □ 许可证不明的已标出，未默认为宽松型
- □ 著佐权和非 OSI 的发现已阅读许可证原文，不只看元数据
- □ 引用已注明出处，未核实的已标〔待核〕
- □ 审批人已具体到人
- □ 已加内部工作成果标识
