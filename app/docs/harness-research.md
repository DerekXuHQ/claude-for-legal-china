# 法律助理的回答框架：怎样让中档模型交出专业、能直接用的意见

2026-11-04 调研。前两份调研（`legal-ai-research.md` 讲产品与评测，`scenarios-research.md` 讲场景目录）已经写过的内容这里不再重复，只补充它们没有覆盖的三件事：中国律师的书面成果长什么样、哪些框架手段有证据、中国法场景下模型具体会错在哪里。最后给出对本 App 框架的改动清单、输出约定和定稿前核对清单。

前提：模型（gpt-6-luna）换不了，能改的是提示词、流程、检索步骤和程序核对。之前的实测结论是：先研究后写的多智能体流程（`consult.mjs`）更慢、效果没有更好；有原文支撑的核对是确实有效的改进；没有原文的自我批评往往让结果更差。下面的建议都按这个前提来排。

## 一、证据摘要

### 1. 中国律师的书面成果：客户觉得能用的是什么样

**法律意见书 / 备忘录**

- 君合律师周烽（2025-12）总结：客户要的是答案，分析了各种观点却没有结论的备忘录不合格；「律师的法律意见不能止于不确定性」。不确定的地方用简短的范围说明交代，免责声明写长了会显得只顾保护自己。可读性方面：客户关心的地方详写，其他略写；给业务人员看要解释概念，给法务看可以省；多用分类、表格、要点、举例。常见扣分项：只罗列观点没有结论、引用没有出处、术语未定义、序号错误。结构上推荐 CRAC（结论前置），并指出事实前提不清时应先向客户确认前提问题。<https://www.junhe.com/legal-updates/2852?locale=zh>
- 深圳律师网的写作说明把正文分为五块：客户目标 → 事实概要 → 法律分析 → 方案对比（对策、程序、费用、优劣与风险）→ 结论。几条要求：事实要注明来源（客户提供还是独立调查）；先把客户目标发给客户确认；「标题即观点」，每段先写中心句；确属违法的必须明确说，不得含糊。<https://www.quanlv66.com/m/info.php?cid=309&id=2202>
- 江西省律协《律师出具法律意见书指引》（据检索摘要；原页面抓取失败，未能逐条核对）：结论性意见要列明所依据的主要法律法规，并核查所引法规是否仍然有效。<http://www.jxlawyer.com/index.php?m=content&c=index&a=show&catid=273&id=8635>
- 证券法律业务执业规则（证监会、司法部）对质控的要求：查验要有计划和书面记录；不同来源的证据结论互相矛盾时，必须追加程序查证。<https://law.asia/zh-hans/csrc-regulates-securities-law-practices-lawyers/>
- 国外备忘录写作通行的做法：事实部分只写决定结论的事实，对客户有利和不利的都写，不在事实部分评论。<https://www.law.cuny.edu/academics/academic-resources-support/legal-writing-center/student-resources/drafting-a-law-office-memorandum/>

**合同审查意见、律师函、答辩状**

- 合同审查：业内工具和律师普遍采用高/中/低三档风险，每条写「问题 → 后果 → 可以直接替换的文字」，配合修订稿交付。Spellbook、Legora 的 playbook 都是「首选立场 + 按优先顺序排列的后备立场」（厂商自述）。<https://support.legora.com/en/articles/309366-playbooks> <https://www.spellbook.legal/learn/contract-playbook>。本 App 的 `review.mjs` 已经是这个结构，不需要大改。
- 答辩状：先逐条列出对方的全部诉讼请求，逐项回应（认可 / 部分认可 / 不认可），再单独写抗辩理由和证据。可以确定的事实就承认，全盘否认会损害可信度。<https://www.americanbar.org/groups/litigation/resources/litigation-journal/2026-winter/the-architecture-of-reply>
- PLawBench（阿里/Qwen 等，2026-01）对文书生成的评分细则同样要求「逐点回应（答辩）」「审查请求金额」「对管辖规则敏感」，并发现所有被测模型都会犯「没有逐点回应」「不审查对方主张的金额」这类错误（见下文第 4 节）。
- 律师函：通行结构是事实背景 → 法律依据 → 明确的要求事项 → 履行期限 → 逾期后果 → 保留权利。要点是每一个事实都要核实，避免不当自认，后果只写真能做到、法律允许做的（写过头可能构成敲诈或引来反诉）。<https://translate.hicom-asia.com/area/lawyers-letter-structure> （来源权威性一般，结构与国内通行做法一致）

**小结**：客户能直接用的书面意见有几个共同点：结论放最前面而且明确；事实和假设写清楚、注明来源；每个结论都有现行有效的依据；给出可比较的方案（成本、时间、风险）；下一步是能照着做的动作，带期限。本 App 现有的 SYSTEM_PROMPT 大方向是对的，缺的是两样：一是**把这些要求变成能检查的格式**，二是**程序核对**。

### 2. 专业法律 AI 产品怎么保证输出能用（多为厂商自述）

| 产品 | 公开说法 | 对我们的启发 |
|---|---|---|
| Thomson Reuters CoCounsel Deep Research | 先拟多步研究计划，遇到歧义会停下来问；成文法是核心依据时会识别 KeyCite 的红黄旗（被推翻、被质疑）并写进分析；报告里每个引用都带可核对的链接。<https://legal.thomsonreuters.com/blog/what-true-deep-research-looks-like/> <https://www.lawnext.com/2025/08/thomson-reuters-launches-cocounsel-legal>（厂商自述） | 依据的**效力状态**要进入分析本身，不能只是事后标注 |
| Lexis+ with Protégé | 每个请求经过语义理解、**时效过滤**、权威排序、**引用校验**等五个阶段；无法链接到原文的引用标出来交人工核实。<https://www.lexisnexis.com/community/insights/legal/b/thought-leadership/posts/legal-ai-citation-integrity>（厂商自述）。斯坦福独立测评仍测出 17% 以上的幻觉率 | 「能链接」不等于「支持结论」，见第 3 节「错误挂靠」 |
| Harvey | BigLaw Bench 用「source score」衡量事实陈述能否追溯到来源；Harvey 自己也承认，用提示词逼模型给细到段落的出处，答案质量会下降。<https://www.harvey.ai/blog/biglaw-bench-sources>（厂商自述）；任务含糊时停下来问一个有针对性的问题（路线图页面） | 不要让模型在写作时兼顾细粒度出处，**出处核对交给写完之后的程序和单独一轮** |
| Spellbook / Legora | Playbook：首选立场 + 后备 1–3；按立场改写条款（厂商自述） | 已在 `review.mjs` 实现 |
| 通义法睿 | 精调 + RAG + 法律 Agent；回答可回溯到法条原文（第三方评测文章）；案例检索支持按法规时效筛选。<https://help.aliyun.com/document_detail/2778916.html> <https://guantao.com/page3908> | 时效筛选是标配 |
| 元典问达 | 可溯源答案 + 对检索结果「反向核验」（英文报道转述）。<https://besthub.dev/articles/how-ai-is-transforming-legal-research-inside-the-yuandian-wenda-smart-q-a-engine-973d50dd8dfa> | 与本 App 的引用核对思路一致 |
| 得理 | AI 类案报告固定分五块：检索目的、检索情况、检索结果、总结分析、争议问题（应用商店页面）。<https://www.delilegal.com/news/company/NKXfTjoVBIjHRlcDmrTyFvjJrrtnnuNg> | 类案输出也应有固定结构 |
| 观韬律所对 MetaLaw、通义法睿的实测 | 问题：结论引用的案例带随机性，不优先引用指导性案例和公报案例；**二审已改判的案件，仍引用一审说理**；同一问题多次检索结论不同；律师建议换同义词多检索几次。<https://guantao.com/page3908> | 案例的效力和审级要进入核对；检索要换说法 |

iCourt AlphaGPT（意见书含时间轴、诉讼可行性、风险评估）、幂律（高/中/低风险，审查点数百个）在 `legal-ai-research.md` 里已经写过，这里不再展开。

**共同做法**：(1) 有效性/时效过滤放在检索层；(2) 引用都链接原文，对不上的显式标出；(3) 有歧义先问；(4) 固定的交付结构。没有一家公开声称靠模型「自我反思」来提升质量。

### 3. 框架与提示技巧：哪些有证据

| 手段 | 证据 | 强度 | 结论 |
|---|---|---|---|
| **边检索边推理（ReAct）做研究，写文书时先列结构** | LegalAgentBench（中文法律智能体基准，37 个工具，300 题）：8 个模型里有 7 个用 ReAct 的成功率最高（GPT-4o 79.1%，Plan-and-Solve 47.6%）；但在**写作**任务上反过来，先计划更好（GPT-4o 写作 ReAct 65.4% / P-S 79.7%；Claude-sonnet 65.7% / P-E 86.1%）。主要错误：该查法律时没查、读不懂条文、工具参数错误、原地打转。<https://arxiv.org/html/2412.17259v1> | 中（单一基准，但正好是中文法律 + 工具场景） | 保留单个 ReAct 检索代理（与本 App 的实测一致）；**文书类交付物**单独用一步「先列提纲再写」 |
| **法律三段论结构**（大前提-小前提-结论） | Legal Syllogism Prompting：在 CAIL2018 上零样本优于普通提示和 CoT（GPT-3 时代）。<https://arxiv.org/abs/2307.08321>。PLawBench：各模型在实务案例分析中「法条」和「推理」两项都低于平均分，原因是**不按三段论走，跳步、漏掉核心法条**；同时评分按「结论 / 法条依据 / 案件事实 / 推理过程」四块打分。<https://arxiv.org/abs/2601.16669> | 中 | 在输出约定里，每个争点按「规定 → 本案事实 → 结论」写，不另加推理轮 |
| **检索词改写 / 同义词扩展** | STARD（1,543 个真实非专业人士的提问）：现有检索方法在普通人的说法上明显吃力，最好的方法 Recall@100 为 0.907。<https://arxiv.org/abs/2406.15313>。LegalMALR（2026）：多角度的法律化改写 + LLM 重排，在 STARD 和 CSAID 上明显优于 RAG 基线。<https://arxiv.org/abs/2601.17692>。观韬实测也建议换同义词 | 中–强（本 App 是 BM25 关键词检索，受影响更大） | 在 `runTool` 层做**确定性**同义词扩展（零延迟），提示词里的「换几种说法」保留 |
| **读原文而不是摘要；检索要精确** | LegalBench-RAG：检索单元越精确越好，无关的大段文本会增加幻觉。<https://arxiv.org/abs/2408.10343>。斯坦福：「检索不到最相关的来源」占幻觉回答的 20%–47%。<https://arxiv.org/html/2405.20362v1> | 中 | 条文单位很小，读全文没有成本问题；要补的是**条文里引用的其他条文**和**对应的司法解释** |
| **效力与版本检查** | PLawBench：除 DeepSeek 外，5 个前沿模型都出现过「引用旧版本或已废止条文」，GPT 系列尤其明显。<https://arxiv.org/abs/2601.16669>。CLaw：中国法律修订频繁，多数模型无法准确复述条文、也分不清历史版本，作者结论是必须靠检索。<https://arxiv.org/abs/2509.21208>。斯坦福：「不适用的依据」（辖区不对、已被推翻）占幻觉回答的 23%–38% | 强 | 版本检查交给程序，不要指望模型自己记得 |
| **有原文的核对（逐条对照）** | Chain-of-Verification：先拟核对问题，**独立**回答（不看草稿），再修订；在长文本生成上明显减少编造。<https://arxiv.org/abs/2309.11495>。斯坦福把「引用了真实来源但来源并不支持该命题」单列为「错误挂靠（misgrounded）」，是 RAG 工具的主要错误。PLawBench：「条号对、内容错」在 4 个模型中出现 | 强（加上本 App 自己的实测） | 本 App 的首要改进：引用核对从「条号存不存在」升级为「原文支不支持这句话」 |
| **没有外部信息的自我纠错** | Huang 等 2023：没有外部反馈时，模型改自己的推理常常改得更差。<https://arxiv.org/abs/2310.01798>。与本 App 实测一致 | 强 | 不加「请检查你的回答」式的空转复核；复核必须拿着原文 |
| **对错误前提的盲从** | Dahl 等《Large Legal Fictions》：模型经常接受用户错误的法律前提，也不知道自己什么时候在编。<https://arxiv.org/abs/2401.01301>。PLawBench：起诉状写作中模型「盲目照办」（替没有诉讼主体资格的人起诉、选错管辖）。斯坦福：迎合错误前提占 0%–6%（检索型工具较低） | 中 | 把用户话里的法律判断（「他违法了」「我要告他」）当作待证命题；文书类任务先做程序审查（主体、管辖、时效） |
| **金额与计算** | PLawBench：「结论不完整（缺计算）」「不审查主张金额」在多数模型中出现。LegalAgentBench 专门配了 5 个数学工具 | 中 | 金额、期限交给确定性计算工具，模型只负责选输入值 |
| **反方论证** | 没有找到直接针对法律回答的实证。PLawBench 记录了「偏向一方」的错误 | 弱 | 只在争议类任务的输出结构里留「对方最可能的抗辩」一栏，要求有依据；不单独加一轮 |

相关基准速查：LegalBench（按 IRAC 拆任务）、LawBench、LexEval（23 任务 14,150 题，GPT-4 最好但仍有大量中国法知识缺口 <https://arxiv.org/abs/2409.20288>）、CAIL、LegalAgentBench、PLawBench、CLaw、STARD。对本 App 最有参考价值的是 **PLawBench 的错误分类**（可以直接用作评测细则）和 **LegalAgentBench 的「研究用 ReAct、写作先计划」**。

### 4. 中国法场景下的具体失败模式与对策

综合 PLawBench 错误表（表 5–7）、斯坦福错误分类、CLaw、观韬实测和中国法的实际情况：

| 失败模式 | 典型例子 | 对策（本 App 能做的） |
|---|---|---|
| 引用已废止的法律 | 《合同法》《民法通则》《物权法》《担保法》《侵权责任法》《婚姻法》《继承法》（2021-01-01 起被民法典取代）；原劳动争议司法解释（一）至（四）（被 2020 年的解释（一）取代） | 程序维护「已废止 → 现行对应」映射表，`verify.mjs` 命中就标红并提示替代依据 |
| 新旧版本条号错位 | 公司法 2018 版与 2023 版（2024-07-01 施行）条号大幅变动；模型按记忆写「公司法第 X 条」，regex 核对会**链接到新版同号但内容不同的条文** | 核对时比对条文原文与句子内容（见改动 1）；行为发生时点早于新法施行的，用旧版本核对 |
| 漏掉新规 | 劳动争议解释（二）（2025-09-01 施行）、公司法注册资本五年实缴、2026 年商标法修订（2027-01-01 施行）等 | 场景卡片的核心依据由程序预取（改动 5）；SYSTEM_PROMPT 保留「尚未生效」提示 |
| 把征求意见稿、草案当成现行规定 | 「XX 办法（征求意见稿）规定……」 | 资料库不收录征求意见稿；正文里出现「征求意见稿」「草案」时程序加提示 |
| 条号对、内容错 / 条号错、内容对 | 把第四十七条（经济补偿）的内容挂在第四十六条上 | 有原文的逐句核对（改动 1） |
| 一般法、特别法用反 | 用民法典违约金规则处理劳动合同违约金（劳动合同法第二十五条限定只有两种情形可以约定） | 输出约定要求写明「为什么适用这一条而不是那一条」；领域手册的「容易出错的地方」保留 |
| 混用地方规定 | 用上海的社平工资、北京的工伤待遇标准回答深圳的问题；把某地高院的会议纪要当全国规则 | 程序检查：引用的地方性规定与用户地区不一致时标出（改动 6） |
| 金额过于自信 | 「您可以拿到 2N 共 12 万」，没有说明基数、封顶、年限折算和前提 | 计算工具 + 「金额必须给出公式、输入值来源和区间」（改动 7） |
| 期限算错 | 仲裁时效一年从「知道权利被侵害之日」起算、答辩期 15 日、上诉期 15 日/30 日、复议 60 日、行政诉讼 6 个月、节假日顺延 | 期限计算工具（改动 7）；P1/P9 第一段必须写期限 |
| 泛泛而谈 | 「建议协商解决，必要时咨询专业律师」 | 输出约定要求下一步写成「谁、在哪天之前、做什么、留什么证据」；程序检测空话（改动 9） |
| 盲从用户的定性 | 用户说「员工严重违纪」就直接按过失性解除分析 | 「事实与假设」一节把用户的定性当作待证事实 |
| 案例效力 | 引用「不再参照」的指导性案例；二审已改判仍引用一审观点 | 已有 status 字段；核对时程序检查（改动 6） |
| 只回答字面问题 | 问「能不能扣工资」，漏了「扣完之后员工被迫解除要付经济补偿」 | 输出约定里固定一栏「你没问但会影响结果的」 |

## 二、对本 App 框架的改动建议（按优先级排序）

排序依据：证据强度 × 对「专业、能直接用」的影响 ÷ 延迟和成本。每条都可以用 `scripts/eval.mjs` 做前后对比。延迟按 gpt-6-luna 的一次中等长度 JSON 调用约 5–15 秒估算。

### 1. 引用核对升级为「原文是否支持这句话」（逐句对照）

- **改什么**：在现有 regex 核对之后增加一轮「依据对照」。程序从答案中抽出每个带 `[[art:…]]` 或「《某法》第某条」的句子，按编号从资料库取条文原文（不经模型转述）。然后用一次 JSON 调用（低推理强度，**不给它看完整草稿，只给句子 + 原文**，即 CoVe 的「独立核对」）判断每一对是「支持 / 部分支持 / 不支持 / 条文无关」，不支持的给出一句改写或删除建议。程序只替换被判为不支持的句子，或者在句后加〔依据不足〕，不重写全文。
- **文件 / 函数**：`verify.mjs` 新增 `groundCheck(db, text, settings)`；`ask.mjs` 中 `verifyCitations` 之后调用；`review.mjs` 的第 ④ 步可以复用。
- **预期效果**：直接压低「错误挂靠」和「条号对、内容错」，这是 RAG 型法律工具最主要的错误。这也是本 App 已经测出有效的方向。
- **证据**：强（CoVe、斯坦福 misgrounded 分类、PLawBench 法条错误、本 App 实测）。
- **成本**：+1 次调用，约 5–12 秒；输入约 2–6k tokens（句子 + 条文，条文按 600 字截断）。没有引用的回答跳过。界面上先流式显示草稿，核对完成后再更新修改过的句子，用户感受到的等待不长。

### 2. 证据账本：记录本次实际读过的原文，核对时区分「读过 / 没读过 / 不存在」

- **改什么**：`runAgent` 在执行 `read_articles`、`read_case`、`read_guide`、`compare_versions` 时，把返回的编号、版本和施行日期记进 `ledger`。核对时分三类：①引用的条文本次读过原文：正常；②资料库里有但本次没读：程序自动取原文，交给改动 1 对照；③资料库里没有：保留现在的〔资料库未核实〕。`search_law` 只返回摘要，摘要命中不算「读过」。
- **文件 / 函数**：`agent.mjs` 的 `runAgent` 返回 `{ messages, text, ledger }`；`ask.mjs` 把 ledger 传给 `verify.mjs`。
- **预期效果**：改动 1 的输入更准；还能统计「依据完整度」，用于改动 10 的把握程度。还能抓出「只看了检索摘要就下结论」的情况。
- **证据**：中（斯坦福：检索不足 20%–47%；LegalAgentBench：该查不查）。
- **成本**：几乎为零（纯程序）。

### 3. 版本与时点门控：按「行为发生时」核对适用版本，程序拦截已废止的法律

- **改什么**：
  - 分流（`routeTask`）多输出一个字段 `fact_date`（行为或事件发生的时间，看不出来就留空），追问清单里时间不明且会影响适用版本的，就问一句。
  - `verify.mjs` 的 `findDoc` 目前只匹配现行版本。改为：有 `fact_date` 时，选当时施行的版本核对；同一法律的现行版与当时版本条文内容不一样的，在引用后注明「行为发生时适用 20XX 年版，该条内容为……」。
  - 增加一张「已废止 → 现行对应」映射表（合同法 → 民法典合同编，民法通则/物权法/担保法/侵权责任法/婚姻法/继承法/收养法/民法总则 → 民法典相应编；原劳动争议解释（一）至（四）→ 2020 年解释（一）等）。答案中出现这些名称时，程序加〔已废止，现行依据为……〕。如果是在讲新旧衔接，就不标（判断依据：同一段里同时出现了现行法名称）。
  - 正文出现「征求意见稿」「草案」时，提示「尚未生效，不能作为依据」。
- **文件 / 函数**：`router.mjs`（`routeTask` 输出格式）、`verify.mjs`（`findDoc`、新增 `REPEALED` 映射表）、`ask.mjs` 把 `fact_date` 放进用户消息的方括号提示里。
- **预期效果**：去掉 PLawBench 里几乎所有模型都会犯的「旧版本 / 已废止」错误，也修掉本 App 现有 regex 核对把旧条号链接到新版同号条文的问题（公司法 2018 版和 2023 版并存于资料库，正是这种风险）。
- **证据**：强。
- **成本**：分流多一个字段，几乎无成本；核对为纯程序。

### 4. 检索层的法律同义词扩展（确定性，零延迟）

- **改什么**：`search_law` 在调用 `search.searchArticles` 前，用一张口语 → 法律术语的映射表扩展检索词，扩展词作为 OR 补充项，排序时排在原词命中之后。例如：辞退/开除/炒鱿鱼 → 解除劳动合同；赔偿（劳动场景）→ 经济补偿、赔偿金；押金 → 定金、保证金；老赖 → 失信被执行人；欠钱不还 → 借款合同、逾期利息；跳槽去对手公司 → 竞业限制；工伤 → 工伤认定、停工留薪期；罚款（公司罚员工）→ 规章制度、扣除工资；产假 → 女职工劳动保护、产假；退钱 → 退货、解除合同、预付款。映射表从 99 个场景的 `examples` 和 `laws` 里整理，先做 200–300 条。返回结果里注明「已按 X 扩展」，让模型知道检索过哪些说法。
- **文件 / 函数**：`agent.mjs` 的 `runTool` → `search_law`；映射表放 `server/ai/synonyms.json`。
- **预期效果**：BM25 关键词检索对普通人的说法召回差（STARD），扩展词之后能减少「漏掉核心法条」（PLawBench 里 6 个模型全都出现）。
- **证据**：中–强。
- **成本**：零延迟；token 略增（结果条数不变）。

### 5. 场景核心依据由程序预取，放进系统提示

- **改什么**：每个场景卡片的 `laws` 字段已经写了主要依据名称。把它整理成具体条文编号清单（构建时由 `scripts/build-scenarios.mjs` 解析并对资料库核对），回答前由程序直接读出原文（像 `review.mjs` 的 `integrityPack` 一样），作为「本场景核心条文（已读原文）」放进系统提示，并计入证据账本。模型仍可以继续检索补充。有地区时，同时按地区预取 `search_law(province=…)` 的前 3 条地方规定（只放标题和条号，需要时再读）。
- **文件 / 函数**：`tasks.mjs` 的 `getScenario` 增加 `core_articles`；`ask.mjs` 拼 system 时加入；`build-scenarios.mjs` 生成。
- **预期效果**：解决「该查不查」（LegalAgentBench）和「漏掉核心法条」，同时减少 2–4 轮检索，**可能反而更快**。
- **证据**：中。
- **成本**：系统提示 +2–5k tokens；检索轮数减少，总延迟预计持平或下降。

### 6. 程序检查地区、案例效力和层级冲突

- **改什么**：`verify.mjs` 对每个被链接的依据做三项检查：①地方性法规的 `province` 与用户地区不一致的，标〔非本地规定〕；②指导性案例 status 为「不再参照」的，标出；③同一句里引用了下位法、却与上位法的数字冲突（例如地方规定的比例与法律不同）的，暂时只记录不处理，交给改动 1。另外在 `read_articles` 的返回中，把条文里「依照本法第 X 条」「前款」「第 X 条规定的情形」所指的条文编号一起列出（`refs` 字段），让模型知道还该读哪几条。
- **文件 / 函数**：`verify.mjs`；`agent.mjs` 的 `runTool` → `read_articles`。
- **预期效果**：减少「不适用的依据」（斯坦福 23%–38%）和地方规则混用。
- **证据**：中。
- **成本**：零（纯程序）。

### 7. 金额与期限计算工具

- **改什么**：新增两个确定性工具。
  - `calc_amount`：经济补偿 N（年限折算：满 6 个月按 1 年、不满 6 个月按半个月）、2N、代通知金、月工资基数与当地社平三倍封顶及十二年封顶、二倍工资差额、加班费（1.5/2/3 倍）、违约金与定金上限（定金不超过主合同标的额 20%）、逾期利息（LPR 倍数）。输入值必须写明来源（用户提供 / 假设 / 资料库条文编号），输出算式和结果。社平工资、最低工资这类地方数据资料库里没有的，返回「需用户提供或另行核实」，**不让模型自己填数**。
  - `calc_deadline`：起算日 + 期间（日/月/年）+ 是否节假日顺延 → 截止日，附依据条文编号。常用期间做成预设：劳动仲裁时效 1 年、民事诉讼时效 3 年、答辩期 15 日、上诉期 15 日（判决）/10 日（裁定）、行政复议 60 日、行政诉讼 6 个月、陈述申辩期等。
  - 输出约定要求：答案中凡出现金额和截止日，必须来自这两个工具的结果，或者写明「估算，前提是……」。核对时，程序检查答案里的金额、日期是否出现在工具输出里，不在的就标〔未经计算核对〕。
- **文件 / 函数**：`agent.mjs` 的 `TOOLS` / `runTool`；新文件 `server/ai/calc.mjs`；`verify.mjs` 增加数字比对。
- **预期效果**：修掉「金额过于自信」「缺计算」「不审查主张金额」；P1、P4、P12 三条流程最受益。
- **证据**：中（PLawBench、LegalAgentBench 的数学工具）。
- **成本**：每次工具调用多一轮模型往返（约 2–4 秒）；计算本身为零。

### 8. 按任务类型固定输出结构，程序检查格式，缺什么只补什么

- **改什么**：用下文第三部分的「输出约定」替换 SYSTEM_PROMPT 的「## 输出」一节，并在每条流程（`pipelines.mjs` 的 `steps`）末尾注明对应的结构编号。答案写完后，程序检查必备标题（如「结论」「事实与假设」「依据」「下一步」）和结论块是否齐全；缺少的话，只针对缺少的部分追加一次短调用补写（不重写全文）。
- **文件 / 函数**：`agent.mjs` 的 `SYSTEM_PROMPT`；`pipelines.mjs`；`ask.mjs` 增加 `checkFormat()`。
- **预期效果**：结论先行、事实与假设分开、下一步可执行，这是律师和客户最看重的「能用」。固定的标题也让改动 1 的句子抽取更稳定。PLawBench 的评分也是按这几块打分。
- **证据**：中（中国律师写作惯例 + PLawBench 的结构化评分）。
- **成本**：格式检查零成本；需要补写的情况估计不到 20%，每次约 5 秒。

### 9. 「事实与假设」和用户定性分开；用程序检测空话

- **改什么**：
  - 输出约定里，「事实与假设」一节分三列：用户告诉我们的（标「据您所述」）、我们的假设（标「假设」）、会改变结论的未知事实。用户话里的法律定性（「严重违纪」「违法解除」「对方违约」）只能写进第三列或作为待分析的争点，不能直接当事实用。
  - 程序检测空话：「建议咨询专业律师」「视具体情况而定」「建议协商解决」「请注意相关法律风险」等短语，出现了却没有紧跟具体条件或动作的，在格式检查里一起补写。
- **文件 / 函数**：`SYSTEM_PROMPT`；`ask.mjs` 的 `checkFormat()`。
- **预期效果**：减少盲从错误前提（Dahl、PLawBench 的盲目照办），减少泛泛建议。
- **证据**：中。
- **成本**：零到很低。

### 10. 把握程度由证据决定，不让模型自报信心

- **改什么**：结论块里的「把握」一栏只有三档：**依据明确**（核心条文已读原文，关键事实用户已确认）、**取决于事实**（结论随某个未确认事实改变，要写明是哪个）、**有争议**（条文本身留有裁量空间，或各地裁判口径不一）。程序根据证据账本（核心条文是否读过原文、改动 1 是否有不支持项、追问是否被跳过）给出上限，例如追问被跳过、关键事实是假设的，就不能标「依据明确」。不使用百分比胜诉率。争议类的「大概率支持 / 可能支持 / 大概率驳回」保留，但必须附上理由所依据的条文或事实。
- **文件 / 函数**：`ask.mjs`（根据账本计算上限，写进用户消息的方括号提示）；`SYSTEM_PROMPT`。
- **预期效果**：避免「过于自信」，模型自己不知道什么时候在编（Dahl），所以信心不能让模型自己报。
- **证据**：中（反面证据强：模型自报信心不可靠）。
- **成本**：零。

### 11. 交付物（律师函、答辩状、通知书）单独一步：先列提纲，再起草

- **改什么**：咨询回答里只写文书要点，末尾提供「起草 XX」按钮。用户点击后进入单独的起草步骤：①程序审查（主体资格、管辖、时效、送达方式），有问题先指出，不盲目照办；②按文书类型的固定提纲（见第三部分 F）写出提纲，并列出每段要用的事实和依据编号（来自上一轮的证据账本）；③按提纲起草全文，不再调用检索工具；④跑改动 1 的依据对照。答辩状必须按对方请求逐项回应；律师函的「逾期后果」只写法律允许、用户真能做到的。
- **文件 / 函数**：`pipelines.mjs` 的 P6/P7/P13 和 drafting 手册；`ask.mjs` 新增 `draft` 分支（复用 `runAgent`，`steps` 设小，或直接 `stream`）。
- **预期效果**：LegalAgentBench：写作任务先计划比 ReAct 好 14–20 个百分点；PLawBench：模型普遍不逐点答辩、不审查程序。与「咨询」分开也能缩短咨询回答的长度和时间。
- **证据**：中。
- **成本**：只在用户需要文书时发生：+1 次提纲调用（约 5 秒）+ 起草流式输出。

### 12. 争议类加「对方最可能的抗辩」一栏，但必须有依据，不另加一轮

- **改什么**：P1、P2、P9 的输出结构里加一栏：对方最可能提出的 2–3 个抗辩或主张，各自依据的条文或事实，以及我方怎么应对。必须引用读过的原文；找不到依据的，不写。不加独立的「反方辩论」智能体。
- **文件 / 函数**：`pipelines.mjs`、`tasks/_strategy.md`。
- **预期效果**：减少「偏向一方」，让打法更可信。
- **证据**：弱（专业惯例；没有直接的实证）。
- **成本**：输出多 200–400 字。

### 13. 系统提示的角色和语气：从「律师助理」改成「企业法律顾问」

- **改什么**：开头改为「你是一名在中国大陆执业多年的企业法律顾问……」，并加两条：①用顾问写给客户的口吻，先给判断，再给理由；②不写「作为 AI」「以下仅供参考」，也不写「建议咨询律师」这样的空话；真有必要请律师的，写清楚是什么情形、为什么需要（已有统一免责提示）。领域手册里「律师助理」的字样一并替换。
- **文件 / 函数**：`agent.mjs` 的 `SYSTEM_PROMPT`；`router.mjs` 的两个 system；`tasks/*.md`。
- **预期效果**：符合老板「专业、能直接用、不必像律师助理」的要求。影响主要在语气，对准确性没有影响。
- **证据**：弱（产品判断）。
- **成本**：零。

### 14. 评测集按 PLawBench 的错误分类扩充，并加入版本陷阱题

- **改什么**：`eval/cases.jsonl` 的评分要点增加：「旧版本 / 已废止」「条号对内容错」「一般法特别法用反」「缺计算」「未审查对方金额」「未逐点回应」「盲从用户定性」「地方规定混用」。新增 10–15 道陷阱题，例如：2023 年发生的公司股东出资纠纷（应适用 2018 版公司法）、用户引用《合同法》第 X 条提问、深圳员工问上海的社平封顶、员工自称「被违法辞退」但事实是试用期不符合录用条件。目前 `eval/results` 里多数是单题试跑，改动 1–7 上线前后需要跑完整集。
- **文件 / 函数**：`eval/cases.jsonl`、`scripts/eval.mjs`（评分 prompt 加上这些扣分项）。
- **预期效果**：每项改动都能量化验证，避免再出现「看起来更专业、实际没更好」的情况（`consult` 流水线就是前车之鉴）。
- **证据**：强（方法论）。
- **成本**：只发生在离线评测。

### 不建议做的

- 不加没有原文的「自我复核」「再想一遍」。证据和本 App 实测都表明这会让结果变差。
- 不把单个检索代理换回多研究员流水线（`consult.mjs`）。实测更慢且没有更好，LegalAgentBench 也显示检索阶段用 ReAct 最好。
- 不在写作时要求模型给出细到「款、项」的出处，出处交给程序核对（Harvey 自己的经验：这样做会拉低答案质量）。
- 不让模型自填社平工资、最低工资、LPR 等数据。资料库没有的，就请用户提供或注明待核实。

### 建议的实施顺序

第一批（一周内，几乎都是程序改动）：2 → 3 → 6 → 4 → 13。第二批：1 → 7 → 8/9/10（一起改提示词和格式检查）。第三批：5 → 11 → 12。每一批跑一次完整评测（改动 14 先做）。

## 三、改进后的输出约定（替换 SYSTEM_PROMPT 中的「## 输出」）

下面的文字可以直接放进 `SYSTEM_PROMPT`。各流程在 `pipelines.mjs` 的 `steps` 末尾写「输出按结构 X」。

```markdown
## 输出约定（每个回答都必须遵守）

### 结论块（所有类型都放在最前面，不加标题前的寒暄）
**结论**：一两句话直接回答问题（能 / 不能；合法 / 有风险 / 违法；大概多少钱；最晚哪天）。
**把握**：依据明确 / 取决于事实（写明取决于哪一项）/ 有争议（写明争议在哪里）。不用百分比。
**最要紧的一件事**：现在最该做或最不能做的一件事，有期限的写日期。

### 共同要求
- 每个结论都要能对应到读过原文的条文，按「规定是什么 → 本案事实 → 所以怎样」写，不跳步。
- 「事实与假设」把三类信息分开写：据您所述的事实；我们的假设；会改变结论、还需要确认的事实。用户的定性（如「严重违纪」「对方违约」）当作待分析的问题，不当作事实。
- 金额、期限必须来自计算工具，或者写明「估算，前提是……」，并写出公式和每个输入值的来源。
- 下一步写成「谁、在哪天之前、做什么、留下什么记录」。不写「建议协商」「视情况而定」「咨询专业律师」这类空话；确实需要律师的，写明是哪种情形、为什么。
- 用户没问、但会直接影响结果的风险，单列「你没问但要注意的」，最多三条。
- 引用格式见上；地方规定写明地区；行为发生在新法施行前的，写明适用哪一版。

### 结构 A：法律咨询与合法性判断（general、legality、P8、P11）
1. 结论块
2. 事实与假设
3. 分析：按争点分小标题（标题就是该争点的结论），每个争点：规定 → 本案事实 → 结论；需要排除的规定也写一句为什么不适用
4. 合规的做法 / 替代方案（P8：红黄绿，说明怎么改才能达到同样的商业目的）
5. 你没问但要注意的
6. 下一步（含期限）与需要准备的材料

### 结构 B：被动应对争议与监管（P1、P9）
1. 结论块（「最要紧的一件事」必须是期限）
2. 期限表：事项｜截止日｜起算依据｜不做的后果
3. 对方主张逐项拆解表：请求｜金额｜法律上能否成立｜我方抗辩点｜要用的证据｜评估（大概率支持 / 可能支持 / 大概率驳回，附理由）
4. 风险区间：最好 / 最可能 / 最坏，每档写金额、时间和前提；对方要价与法律上能拿到的分开写
5. 对方最可能的抗辩或主张及应对（有依据的才写）
6. 证据：已有｜缺少｜怎么合法补强｜谁在哪天前完成
7. 打法：和解方案（开价 / 目标 / 底线，话术要点，和解协议必备条款）或应诉准备
8. 事实与假设；需要补充的材料

### 结构 C：主动追讨与执行（P2、P3）
1. 结论块（值不值得追、大概能拿回多少、时效是否还在）
2. 权利是否成立与金额计算（附计算表）
3. 证据与补强
4. 对方偿付能力：需要用户去官方渠道查的项目清单
5. 路径与时间表：每一步的触发条件、时间、费用、对关系的影响
6. 对方最可能的抗辩及应对；禁区（不能用的施压方式）
7. 下一步与文书清单（可一键起草）

### 结构 D：用工处置方案（P4）
1. 结论块（推荐路径、预计成本区间）
2. 事实与假设
3. 路径比较表：路径｜适用条件｜本案是否满足｜所需证据｜成本（0 / N / N+1 / 2N）｜风险｜所需时间
4. 推荐路径的证据搭建与操作时间轴（第几天、谁、做什么、留什么记录）
5. 金额测算表（计算工具结果）
6. 谈判方案；不能做的事
7. 文书清单（可一键起草）

### 结构 E：期限与金额计算（P12）
1. 结论块（结果和截止日）
2. 输入值表：项目｜取值｜来源（用户提供 / 假设 / 条文编号）
3. 计算过程（计算工具的算式）
4. 敏感性：哪个输入值变了，结果怎么变
5. 需要核实的数据（如当地社平工资）

### 结构 F：文书（律师函、答辩状、通知书、协议，P6、P7、P13）
先审程序，再按提纲起草：
- 程序审查：主体是否适格、管辖是否正确、时效与期限、送达方式；有问题先指出，不照办。
- 律师函：事实（只写核实过的）→ 法律依据 → 要求事项（具体到金额、行为）→ 履行期限 → 逾期后果（只写法律允许、真能做到的）→ 保留权利。
- 答辩状：逐项回应对方每一项请求（认可 / 部分认可 / 不认可及理由）→ 对事实逐段表态（认可 / 否认 / 无法确认）→ 抗辩理由 → 证据清单。
- 通知书 / 协议：必备要素清单逐项打勾，送达与签收方式。
- 文末：使用前要补的信息（方括号标出）、要核对的事项。

### 合同与方案审查（P5、plan_review）
沿用 review.mjs 的结构（总体结论 → 必须修改 → 建议修改 → 可以接受但要留意 → 缺失条款 / 合规改造 → 谈判策略 → 签署前确认事项），最前面同样加结论块。
```

## 四、改进后的定稿前核对清单（只能依据已检索到的原文）

分两层：**程序层**（确定性，写在 `verify.mjs` / `ask.mjs`，不依赖模型）和**模型层**（写进 SYSTEM_PROMPT，在最后一轮写答案前执行；改动 1 的依据对照调用也用同一份清单）。核对只能拿本次读过的原文、用户提供的事实和计算工具的输出作为参照，不允许凭记忆判断「这条应该没错」。

### 程序层（自动执行）

1. 每个「《某法》第某条」和 `[[art:…]]`：资料库里有没有；本次是否读过原文（证据账本）；是不是现行版本或行为发生时适用的版本。
2. 法律名称命中「已废止」映射表的：标出并给出现行对应依据（讲新旧衔接的除外）。
3. 出现「征求意见稿」「草案」的：提示尚未生效。
4. 地方性规定的地区与用户地区不一致的：标〔非本地规定〕。
5. 指导性案例 status 为「不再参照」的：标出。
6. 答案里的金额和日期：在计算工具输出或用户事实里找得到；找不到的标〔未经计算核对〕。
7. 结构检查：结论块三项齐全；按任务类型的必备小节齐全；空话短语后面有没有紧跟具体条件或动作。缺什么只补什么。
8. 把握上限：追问被跳过、核心条文没读原文、依据对照有不支持项时，「把握」不能写「依据明确」。

### 模型层（写进 SYSTEM_PROMPT）

```markdown
## 写完之前逐项核对（只依据本次读过的原文和用户给的事实）
1. 每个结论后面挂的条文，原文里真的有支撑这句话的内容吗？条号和内容对得上吗？只是相关、并不支持的，删掉或改写结论。
2. 这条规定在行为发生时有效吗？有没有更新的版本、配套司法解释或特别规定？用了一般规定的，为什么不适用特别规定？
3. 引用的地方规定是不是用户所在地区的？全国规定和地方规定数字不同时，写明以哪个为准、为什么。
4. 每个金额、期限：公式写了吗？每个输入值的来源写了吗？用了计算工具吗？没有的，改成区间并写明前提。
5. 用户的说法里有没有被我当成事实的法律定性？关键事实是用户说的、还是我假设的？有没有分开写？
6. 结论会因为哪个未确认的事实而改变？写进「取决于事实」，并列入需要补充的材料。
7. 对方会怎么反驳？我有没有因为站在用户一边而漏掉对用户不利的条文或事实？
8. 程序上有没有硬伤：主体资格、管辖、时效、前置程序（例如劳动争议须先仲裁）、送达？
9. 下一步是不是能照着做：谁、哪天之前、做什么、留什么记录？
10. 有没有没读原文、只凭检索摘要或记忆写下的依据？有的话，要么现在去读，要么写明「资料库中未检索到，需另行核实」。
```
